## 一、协议基础

### 1. Socket、TCP、UDP、HTTP 和 WebSocket 有什么关系？

**答案：**

分层回答：

- Socket：操作系统提供的网络编程接口，抽象"IP + 端口"通信端点，是使用 TCP／UDP 的手段。
- TCP／UDP：传输层协议。TCP 面向连接、可靠有序字节流；UDP 无连接数据报。
- HTTP：应用层请求—响应协议；HTTP/1.1、HTTP/2 基于 TCP，HTTP/3 基于 QUIC／UDP。
- WebSocket：经 HTTP Upgrade 握手后升级为全双工消息通道，适合服务器主动推送。

游戏典型选型：登录、支付、配置下载走 HTTP(S)；实时战斗状态走 UDP 自定义协议；聊天、推送走 WebSocket 或长连接。

### 2. GET 和 POST 有什么区别？

**答案：**

- 语义：GET 获取资源，安全（不改变服务端状态）且幂等；POST 提交数据交服务端处理，不保证幂等。
- 形式：GET 参数放 URL 查询串，可缓存、可收藏；POST 数据放请求体。
- 澄清两个高频误区：机密性差异为零——明文 HTTP 下 POST 请求体同样是明文，安全靠 HTTPS；"GET 只能 2KB"是浏览器与服务器的实现限制，HTTP 协议本身没有规定 URL 长度上限。

### 3. 大 JSON 接口不常变化，如何利用 HTTP 缓存节省流量？

**答案：**

协商缓存机制：

1. 首次请求：服务端返回 200 + 正文，并带验证器 ETag（内容哈希）或 Last-Modified，配合 Cache-Control 设置缓存周期。
2. 再次请求：客户端缓存正文与验证器，发送 `If-None-Match: <ETag>` 或 `If-Modified-Since: <时间>`。
3. 服务端校验：内容未变返回 304 Not Modified（无正文，仅几百字节）；已变返回 200 + 新正文。

进一步优化：大 JSON 拆成"稳定基础数据 + 小增量"分别缓存；开启 gzip／br 压缩；URL 带版本号配合长强缓存（max-age），内容更新时换版本号即可。

### 4. TCP 和 UDP 有什么区别？游戏中如何选择？

**答案：**

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，三次握手 | 无连接 |
| 可靠性 | 确认重传、有序 | 尽力交付，可能丢、乱序 |
| 数据形态 | 字节流 | 数据报，保留消息边界 |
| 拥塞／流控 | 内置 | 无，需自建 |
| 传输效率 | 头部与重传开销、队头阻塞 | 轻量低延迟 |
| 多播 | 不支持 | 支持广播／组播 |

游戏选型：位置、状态等高频更新用 UDP——新状态可以覆盖旧状态，丢包无需重传旧帧；账号、交易、匹配、聊天等要求完整到达的数据用 TCP，或在 UDP 上自建可靠层（如 KCP：序列号 + ACK + 重传 + 拥塞控制）。

## 二、TCP 连接与消息

### 5. TCP 三次握手的过程是什么？为什么需要三次？

**答案：**

```text
客户端 → 服务端：SYN，seq=x
服务端 → 客户端：SYN+ACK，seq=y，ack=x+1
客户端 → 服务端：ACK，ack=y+1
```

作用：双方交换并确认初始序列号（ISN），协商 MSS、窗口缩放等选项，同步连接状态。

为什么必须三次：

1. 补齐双向确认：两次握手时服务端无法确认"客户端能收到自己的报文"，第三次 ACK 补齐了服务端方向的收发能力确认。
2. 防止历史连接：旧的重复 SYN 延迟到达时，三次握手让服务端在收到第三次确认前不建立连接，避免把资源浪费在失效连接上。

### 6. TCP 四次挥手和 TIME_WAIT 的作用是什么？

**答案：**

```text
主动方 → 被动方：FIN（我不再发送）
被动方 → 主动方：ACK（确认；此时可能还有数据要发）
被动方 → 主动方：FIN（我也发完了）
主动方 → 被动方：ACK
```

TCP 是全双工，两个方向独立关闭，因此 FIN 需要四段交互（中间的 ACK 与 FIN 可能合并，抓包不一定恰好四段）。

TIME_WAIT（主动关闭方等待 2MSL）的两个作用：

1. 保证最后一个 ACK 可达：若 ACK 丢失，对方重发 FIN 时可再次确认。
2. 让本连接的旧报文在网络中自然消亡，避免延迟报文串入复用同一四元组的新连接。

### 7. 什么是粘包和拆包？如何处理？

**答案：**

本质：TCP 是字节流协议，没有消息边界，一次 `recv` 可能读到半条消息、恰好一条或多条——"粘包／拆包"是应用层未定义消息边界的表现，不是 TCP 的缺陷。

解决方案：

1. 定长消息：实现简单，浪费带宽，适合固定小包。
2. 长度前缀（最常用）：包头写明包体长度，接收端按长度切分。
3. 分隔符：特殊字符分隔，正文需转义。

接收端实现：维护接收缓冲循环解析——包头不完整则等待；解析出长度后校验合法上限（防止非法长度导致超量分配）；包体不完整继续收；完整后取出一条业务消息并处理剩余缓冲。

## 三、游戏通信

### 8. 心跳、断线重连和请求重试怎么设计？

**答案：**

- 心跳：周期发送心跳包，连续 N 个周期未收到对方响应判定超时断线；同时承担 NAT 连接保活作用。
- 重连：指数退避 + 随机抖动，避免大量客户端同时重连冲击服务器；重连后重新认证、重新订阅状态、按版本号同步增量。
- 重试：每个请求带自增请求 ID；超时不等于服务端没处理，非幂等操作必须靠请求 ID 去重或先查结果再决定是否重发；响应携带请求 ID，用于过滤旧包与重复包。

### 9. 状态同步和帧同步有什么区别？

**答案：**

| 维度 | 帧同步（Lockstep） | 状态同步（Server Authoritative） |
| --- | --- | --- |
| 同步内容 | 只同步玩家输入／指令 | 同步实体状态与快照 |
| 逻辑位置 | 全端各自确定性模拟 | 服务器权威模拟，客户端表现 |
| 带宽 | 随玩家数增长，极低 | 随实体数与状态量增长，高 |
| 确定性要求 | 严格：浮点、容器遍历、随机数全部一致 | 无硬性要求 |
| 表现 | 天然一致，易做回放与观战 | 需插值、预测与和解 |
| 断线重连 | 追帧（重放全部指令） | 直接下发当前快照 |
| 反作弊 | 逻辑在客户端，暴露严重 | 服务器权威，天然抗作弊 |

选型经验：MOBA（英雄少、需要回放、带宽敏感）经典选择帧同步；MMO（世界大、实体多、反作弊要求高）几乎只能状态同步；射击游戏常见混合方案——核心状态走状态同步，命中判定按项目放在服务器或客户端。

### 10. 游戏消息如何序列化并降低带宽？

**答案：**

消息头设计：消息类型、版本、长度、实体 ID、序列号／时间戳；接收端校验长度与取值范围，服务端再校验业务权限。

降带宽手段：量化（浮点转定点）、差量同步（只传变化，双方维护基线，基线失效时恢复全量）、压缩、降低更新频率、AOI 兴趣区筛选（只同步玩家关心的实体）。

ProtoBuf 的代表优势：

1. 二进制 tag + varint 编码，不传字段名与类型描述，同内容远小于 JSON／XML。
2. 编解码接近内存拷贝量级，无字符串解析，GC 压力小。
3. `.proto` schema 生成多语言代码，客户端服务器共用一份契约。
4. 按字段编号识别：新增字段老端忽略、废弃编号不复用，向前向后兼容规则明确。

边界：ProtoBuf 不加密，保密靠 TLS；proto3 默认值字段不序列化，不能用"字段缺失"区分默认与未设置；AOT 平台（IL2CPP）注意反射裁剪，必要时改用代码生成方案。
